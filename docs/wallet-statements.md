# Wallet statements and company Proceed fees

Dashboard wallet tiles open a selected wallet statement. The duplicate top Cash/MIO Points card is removed; personal PPV qualification points remain distinct from spendable Shopping Points. Statements have Date/time, Detail, Amount with Received/Paid/Converted labels, and View receipt. Date filters are inclusive Pakistan calendar days. The mobile table scrolls horizontally; the surrounding page does not.

The common history reader uses the earning's saved routing row, not today's bonus settings. Cash excludes network/e-commerce earnings originally routed to Proceed. Other wallets select only their own income-ledger movements. Running balances are calculated over the complete selected wallet before activity/date pagination. Shared events in the cash and income ledgers are not unioned twice. The legacy Cash RPC delegates to the same reader. Admin support uses the same UI and an admin-authorized selected-member RPC.

Proceed conversion retains the configured split and transaction PIN requirement. Processing fees are now sourced from immutable conversion records into the existing company treasury, not credited into the company member's spendable Cash account. Existing fee credits receive a linked, idempotent `admin_burn` reclassification; original and correction ledger rows are retained for audit. The member statement excludes the pair, since the fee is company income. Insufficient Cash during migration causes the atomic migration to fail instead of silently writing a negative balance.

Company Earnings includes a compact Company Proceed Fees statement with source member, date filtering and downloadable receipt. Existing treasury source totals include the fees once. Its API requires an authenticated admin. Member history APIs derive identity from auth.uid(); the private reader and reclassification audit table have no client grants. The intentionally privileged public RPCs enforce ownership/admin checks and an empty search_path.

Apply `supabase/migrations/*_wallet_statements_company_fees.sql` atomically before deploying the UI. Source definitions are `schema/company_proceed_income.sql` and `schema/wallet_history.sql`; `schema/cash_wallet_history.sql` is the compatibility wrapper. Replaying the migration does not repeat historical fee deductions or treasury credits. Concurrent conversion requests serialize on request key before checking replay ownership and amount.

Validation: `tests/wallet-statements.mjs` covers the 150 Cash/50 Proceed example, reclassification and migration replay, exact 75/10/10/5 split, conversion retry isolation, historic Cash routing, e-commerce Proceed routing, local date boundaries, admin/anonymous/own-account permissions. Existing package-history, dashboard, member-support, receipt and interface tests cover UI navigation, package receipt balances, date payloads, account switches, logout races and escaping. Browser QA used fixture data at desktop and 320px widths; production balances and RPC results were verified separately. No new live conversion was made for testing.
